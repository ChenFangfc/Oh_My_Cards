## Reward & cashback engine (8)

### [CRITICAL] Category matching is exact-string only, so every catalog bonus category whose name isn't verbatim identical to a UI category silently pays the default rate

`lib/api-client-react/src/local/local-first.ts:699`

**What goes wrong.** The transaction form only ever sends one of 11 fixed strings (transactions.tsx:86 CATEGORIES = Groceries, Dining, Travel, Gas, Entertainment, Streaming, Online Groceries, Flights, Hotels, Rental Cars, Other). Amex Blue Cash Preferred (catalog id 10) stores its category as "Groceries (US supermarkets, up to $6,000/yr)" @ 0.06 with default "Other" @ 0.01. Logging a $200 purchase with category "Groceries" fails the equality test, falls through to the default, and records cashbackEarned = $2.00 / 1.0% instead of $12.00 / 6%. I parsed the whole catalog: 193 (card, UI-category) pairs in the US market lose their bonus this way — Chase Sapphire Reserve "Chase Travel" 8% -> 1%, Citi Strata Premier "Restaurants" 3% -> 1% for "Dining", Amex Gold "U.S. supermarkets (up to $25,000/yr)" 4% -> 1%, Capital One Venture X "Hotels (via Capital One Travel)" 10x -> 2x, etc. The /suggest page uses a completely different tag-based matcher (scoreCategoryForPurchase, line 3028) that DOES match these names, so Suggest promises "Blue Cash Preferred, 6%, $12.00 expected" and logging the exact same purchase yields $2.00. Zero capped category in the catalog is reachable by exact match, so the entire spend-cap branch of calculateCashback (lines 904-929) is dead code.

**Fix.** Stop comparing raw display strings. Either (a) add a stable machine key to each catalog category (e.g. `matchKeys: ["groceries","supermarket"]`) and match transactions against that, or (b) reuse the tag matcher the suggest engine already has: normalize the category name via getCategoryTags()/findBestCategoryMatch() and pick the highest-rate category whose tags contain the transaction's category tag, falling back to isDefault only when nothing matches. At minimum, strip the parenthetical cap text before comparing and match on the tag set rather than equality, and make transactions.tsx's preview call the same helper.

**Verifier note.** The defect is confirmed as described, with two precision corrections to the write-up that do not change the verdict or severity. First, it is not the case that most bonuses are broken: 132 of the 446 non-default catalog categories DO match a UI category verbatim and work correctly (e.g. CSR "Dining", Blue Cash Preferred "Streaming" and "Gas"). The failure is confined to catalog entries whose names carry qualifiers, caps, or issuer-specific phrasing. Second, a minority of the 193 US pairs are arguably correct behavior rather than silent loss — e.g. Chase Sapphire Preferred's only grocery-ish entry is "Online Groceries" 3%, so an in-store "Groceries" purchase legitimately earning the 1% default is right, not a bug. The unambiguous losses are cases where the catalog holds a bonus that plainly covers the logged UI category but is written with extra text: BCP "Groceries (US supermarkets, up to $6,000/yr)" 6% -> 1%, Amex Gold "U.S. supermarkets (up to $25,000/yr)" 4% -> 1% and "Restaurants worldwide (up to $50,000/yr)" 4% -> 1% for Dining, Citi Strata Premier "Restaurants" 3% -> 1% for Dining, CSR "Flights and Hotels" 4% -> 1% for Flights/Hotels. The dead-spend-cap finding is fully confirmed and is arguably the sharper symptom: 41 catalog categories encode a spend cap and none is reachable by exact match, so lines 904-929 never execute and every capped bonus in the catalog is unenforced.

`lib/api-client-react/src/local/local-first.ts:816`

**What goes wrong.** isBankOfAmericaCustomizedCash matches three catalog cards (id 23 Customized Cash Rewards, id 107 Customized Cash Rewards Secured, id 160 Business Advantage Customized Cash Rewards). ### [HIGH] The BoA keyword "grocery" never matches the UI category "Groceries", so BofA grocery spend earns 1% while "Online Groceries" earns 6%

`lib/api-client-react/src/local/local-first.ts:841`

**What goes wrong.** "Groceries".toLowerCase() === "groceries", and the literal "grocery" is NOT a substring of "groceries" (g-r-o-c-e-r-y vs g-r-o-c-e-r-i-e-s). So on Bank of America Customized Cash Rewards (card 23) a $300 purchase logged as "Groceries": isBoaCustomizedCashBonusCategory returns false for every keyword, the function returns null, control falls to the generic path, "Groceries" does not equal "Grocery Stores & Wholesale Clubs (up to $2,500/quarter)", so it records $3.00 at 1% instead of $6.00 at the card's stated 2%. Meanwhile the UI category "Online Groceries" DOES contain "online", so the same $300 of groceries logged under "Online Groceries" records $18.00 at 6% (first year) — a 6x swing between two adjacent options in the same dropdown for the same purchase.

**Fix.** Match on a normalized token set instead of substrings: e.g. `["grocer", "supermarket", "wholesale"].some(k => normalized.includes(k))` for the 2% test, and order the checks so grocery/wholesale is evaluated before the generic "online" keyword. Better, remove this keyword list entirely per the previous finding and drive it from the catalog category names.

**Verifier note.** The claim is correct but understates the scope in two ways. (1) The 0.02 branch at line 841 is effectively dead code for UI-entered transactions: no string in the CATEGORIES dropdown (transactions.tsx:86-98) contains "grocery" or "wholesale", so the card's stated 2% Grocery Stores & Wholesale Clubs tier can never be earned through the normal transaction flow — the bug is not just a missed match on one label, it disables an entire published earning tier. (2) The same predicate is reused at line 877 for the $2,500/quarter cap accumulator, so grocery spend also never consumes the cap; a user could log unlimited "Groceries" and still have the full $2,500 available for choice-category spend. Additionally, the app's own merchant-inference engine (line 2967, `if (contextTags.has("grocery")) return "Groceries";`) emits the literal "Groceries", so auto-categorized grocery purchases hit the broken path too. Affects the three catalog entries whose names contain "customized cash" under issuer "Bank of America" (id 23, the Secured variant near catalog.ts:8549, and the Business Advantage variant near catalog.ts:12141). Fix: add "groceries" (or use a /grocer|wholesale/ regex) to both the keyword list at line 818-830 and the test at line 841.


### [HIGH] Spend-cap consumption is computed with the same exact-string matcher, so caps never accumulate and the suggest page reports the uncapped bonus rate forever

`lib/api-client-react/src/local/local-first.ts:788`

**What goes wrong.** Logged transactions carry generic categories ("Groceries"), which getCashbackCategory resolves to the card's isDefault category ("Other"), whose name has no cap text, so parseSpendCap returns null and this predicate returns false for every stored transaction. applySpendCapToRate (line 3226) therefore always computes cappedSpendUsed = 0. Concretely: put Amex Blue Cash Preferred in the wallet, log 40 x $200 "Groceries" ($8,000 in 2026, well past the $6,000/yr cap), then open /suggest and type "groceries at Safeway $200". It still returns rate 6%, expectedCashback $12.00 and rulesApplied ["Within $6,000 year cap"], when the correct answer once the cap is exhausted is 1% / $2.00. The same dead predicate is used by calculateCashback (line 915), so no cap ever bites on the logging side either.

**Fix.** Persist the resolved catalog category id (or cap group key) on each Transaction at creation time and sum cap usage by that stored key, instead of re-deriving it from the free-text category on every read. That makes cap accounting independent of the display-name matcher and survives catalog renames.

**Verifier note.** The suggest-page half of the claim is exactly right. The "calculateCashback is broken the same way" half needs correcting: at line 896 getCashbackCategory(card, "Groceries") already fails to match the capped category, so matchedCategory is the 1% isDefault entry and the cap block at line 902 is never entered at all — logged groceries on Blue Cash Preferred earn 1%, not an uncapped 6%. The dead cap predicate is therefore unobservable on the logging side; the observable logging bug there is the separate exact-match category-resolution failure. One exception: Bank of America Customized Cash cards use a separate substring-based path (lines 860-893, isBoaCustomizedCashBonusCategory) that matches generic categories and does accumulate its $2,500/quarter cap correctly at log time — though that path exists only in calculateCashback, not in suggest. Root cause to fix: applySpendCapToRate should attribute prior spend using the same fuzzy category resolution the suggest path uses (or transactions should store the resolved catalog category id), not exact string equality.


### [MEDIUM] Cashback is frozen at insert time and never recomputed, so deleting a transaction leaves later transactions stuck at the post-cap rate

`lib/api-client-react/src/local/local-first.ts:1287`

**What goes wrong.** cashbackEarned/cashbackRate are computed once against the cap usage that existed at insert time and stored on the row; deletion (the only mutation available) never re-runs calculateCashback for the surviving rows. Reachable today through the BoA branch, which does enforce a live $2,500/quarter cap: on Bank of America Customized Cash Rewards, log $2,500 of "Gas" in the quarter (earns $75 at 3%), then log another $500 of "Gas" — correctly recorded at 1% = $5.00. Now delete the $2,500 transaction. The $500 row keeps cashbackEarned = $5.00 / 1.0% even though the quarter's cap is now completely unused; the correct value is $15.00 at 3%. The wallet card's totalCashbackEarned, the dashboard total and analytics all inherit the stale $5.00. The same happens for every capped card once finding 1 is fixed.

**Fix.** After any mutation that changes the transaction set (delete, and any future edit/import), recompute cashback for all affected wallet-card transactions in date order — e.g. a `recalculateCashbackForWalletCard(state, walletCardId)` that replays calculateCashback over the sorted list — or store only the inputs and derive cashback on read.

**Verifier note.** The defect is real as described, with two refinements. (1) It is not limited to the BoA branch pending another fix: the generic capped branch (lines 904-928) is already live because parseSpendCap's regex matches real catalog category strings such as "up to $1,500/quarter" and "up to $6,000/yr", so any such card exhibits the same staleness today. (2) Deletion is not the only trigger. Because the cap-usage sum filters on `date <= transactionDate`, inserting a backdated transaction after a later one also leaves the later row stale — and in the over-crediting direction: log $500 Gas dated Jan 15 (3% = $15), then log $2,500 Gas dated Jan 1 (sees zero prior in-quarter spend, 3% = $75); $3,000 of spend receives the bonus rate against a $2,500 quarterly cap. Root cause: cashbackEarned/cashbackRate are denormalized onto the transaction row at insert time and never re-derived, while the cap calculation they depend on is a function of the whole transaction set.


### [MEDIUM] openedAt is a date-only value parsed as UTC midnight, shifting the first-year bonus window and the annual-fee cycle by a day in negative-offset timezones

`lib/api-client-react/src/local/local-first.ts:847`

**What goes wrong.** wallet.tsx:401 stores `openedAt: new Date(openedAt).toISOString()` where openedAt is the raw "YYYY-MM-DD" from an <input type="date"> (wallet.tsx:497), so "2026-01-01" becomes 2026-01-01T00:00:00.000Z. In America/Los_Angeles `new Date(...)` reads back as 2025-12-31 16:00 local. (a) cycleStartForAnnualFee then takes anchorMonth = 11 and anchorDay = 31, so the cardmember-year window used for currentYearCashback starts 2025-12-31 instead of 2026-01-01 and the wallet's "next annual fee" countdown renders Dec 31, 2026 instead of Jan 1, 2027 — one day of the prior year's transactions is counted toward this year's annual-fee progress. (b) For BoA, a card opened 2025-08-06 has firstYearEnd = 2026-08-06T00:00Z = Aug 5, 5:00 pm local, so a $200 gas purchase made the evening of Aug 5, 2026 records $6.00 at 3% instead of $12.00 at 6%, a full day before the first year actually ends.

**Fix.** Parse date-only values in local time. Store the raw "YYYY-MM-DD" (or build the Date with `new Date(y, m-1, d)` from the split parts) instead of `new Date(str).toISOString()`, and add a `parseLocalDate(iso)` helper used by cycleStartForAnnualFee and getBoaCustomizedCashBonusRate that reconstructs the calendar date in the viewer's timezone.

**Verifier note.** Accurate as stated, with two refinements: (1) the bug only manifests at negative UTC offsets — at UTC+ offsets the UTC-midnight instant still lands on the intended local calendar day, so getMonth()/getDate() are correct; (2) the annual-fee countdown in wallet.tsx:1784-1810 duplicates cycleStartForAnnualFee's anchor logic rather than consuming it, so the UI and engine agree on the same shifted date instead of disagreeing — the error is silent and consistent. Root cause is the date-only string being written through new Date(...).toISOString() at wallet.tsx:401; storing the raw "YYYY-MM-DD" (or constructing it as local midnight) fixes both call sites.

## Billing cycles, balances & benefits (7)

### [HIGH] Unpaid statement balance is silently zeroed the moment the due date passes, so a delinquent card shows $0 due and can never be flagged overdue

`lib/api-client-react/src/local/local-first.ts:1614`

**What goes wrong.** Card with statementClosingDay=20, paymentDueDay=15. Verified with the real computeBillingCycle: on 2026-08-16 the due cycle is Jun 21–Jul 20, previousDueDate = Aug 15, so previousDueHasPassed = true. User charged $1,200 on Jul 10 and recorded no payment. The Jul 20 statement is now one day past due, yet statementBalance and statementSpend are hard-coded to 0. Wallet shows "Due Amount $0" (or only the current-cycle spend), minimumPayment $0, paymentsApplied $0, and nextDueDate jumps forward to Sep 15 with "Due in 30 days". Because nextDueDate is always today-or-later, daysUntilDue can never go negative, so wallet.tsx:1531 `isOverdue = cycle.daysUntilDue < 0 && hasStatementDue` is dead code and the "Overdue by N days" badge can never render. This window recurs every month for the ~5-10 days between the due date and the next statement close.

**Fix.** Do not assume the statement was paid. Keep tracking the closed statement until it is actually satisfied: carry an unpaid remainder forward, e.g. compute `statementBalance = Math.max(0, statementSpendBeforePayments - paymentsSinceDueCycleStart)` unconditionally, and only advance nextDueDate to the current cycle's due date once that remainder is 0. When previousDueHasPassed && remainder > 0, expose it as a past-due amount (negative daysUntilDue against previousDueDate) so the overdue UI can fire.

**Verifier note.** The defect is real and slightly broader than described, but the severity is high rather than critical. Correction to the failure scenario: the wallet does NOT fall back to showing current-cycle spend plus arrears — line 1627 also flips outstandingStart to cycle.currentCycleStart when previousDueHasPassed, so cycle.totalBalance is 0 as well, and wallet.tsx:1519-1522 effectiveCurrentBalance = max(cycle.totalBalance, currentCycleBalance) where currentCycleBalance (wallet.tsx:1460) is likewise anchored at cycle.currentCycleStart. The unpaid $1,200 is therefore excluded from every number in the billing banner, so "Due Amount" renders exactly $0. The dead-code claim is proven, not just asserted: over 313,600 (closingDay, dueDay, date) combinations daysUntilDue was never negative, so the rose "Overdue by N days" banner and all four isOverdue-derived class branches (wallet.tsx:1600-1619, 1715) can never render. Downgrade to high because no money moves and no data is lost: the transaction rows are only filtered out of this query and still appear on the transactions/analytics pages, and wallet.tsx:1456 currentOutstanding still counts them in the no-cycle fallback path. Note also that three separate sites gate on previousDueHasPassed, so this reads as an intentional "presume the statement was paid once the due date passes" simplification — but since the app records payment transactions it can distinguish paid from unpaid, and the zeroing discards information it already has.


### [MEDIUM] After the due date passes, totalBalance/availableCredit restart at the current cycle, dropping carried-over debt and letting prior-statement payments cancel current-cycle purchases

`lib/api-client-react/src/local/local-first.ts:1627`

**What goes wrong.** Same card (close 20 / due 15), today 2026-08-16, currentCycleStart = Jul 21, creditLimit $5,000. Case A (carried debt lost): $1,200 purchase Jul 10, no payment, $150 purchase Aug 2 -> purchasesSince Jul 21 = 150, paymentsSince = 0, totalBalance = $150, availableCredit = $4,850, utilization 3%. Actual owed is $1,350 / available $3,650. Case B (payment applied to wrong cycle): $1,200 purchase Jul 10, $1,200 payment Aug 14 (paying the statement on time), $300 purchase Aug 2 -> purchasesSince Jul 21 = 300, paymentsSince Jul 21 = 1200, totalBalance = Math.max(0, 300-1200) = $0, availableCredit = $5,000, utilization 0%. Actual balance is $300 / available $4,700. The Math.max(0, ...) clamp hides the overpayment instead of restricting the payment to the statement it settles.

**Fix.** Track balance as a running ledger over all transactions (sum of purchases minus payments across full history, or from an explicit statement-carry field) rather than resetting the window at currentCycleStart. Allocate payments to the oldest outstanding statement first, and only let the leftover reduce current-cycle purchases, so neither carried debt nor an over-payment silently disappears.

**Verifier note.** The defect is real but the two cases are not equally attributable to line 1627.

Case B is the true line-1627 defect and is fully valid: once previousDueHasPassed flips, outstandingStart moves to currentCycleStart, but payments dated on/after currentCycleStart that settle the *prior* statement are still counted in paymentsSincePreviousCycleStart while the purchases they paid for are excluded. The payment is netted against unrelated current-cycle purchases, and Math.max(0, ...) at 1644 swallows the excess instead of restricting the payment to the statement it settles. This also hits the very common "paid a few days late" flow (payment dated Aug 18, inside the window): $150 of real current-cycle spend displays as $0 with full available credit.

Case A ("carried debt lost") overstates what line 1627 uniquely causes. The whole balance model only ever looks back two cycles, so the Jul 10 purchase drops out of totalBalance regardless — on Aug 21 the cycle rolls, dueCycleStart becomes Jul 21, and it is excluded even on the previousDueHasPassed=false path. Line 1627 only makes that loss happen 5 days early (closingDay - dueDay). The deeper issue is that the engine has no persisted carried/revolving balance at all: unpaid statement debt older than the due cycle silently vanishes whether or not this branch exists.

Severity medium rather than high: the wrong figures are real, user-facing money numbers (balance, available credit, utilization on the wallet cards) and recur every month, but only during a bounded window of closingDay - dueDay days (5 days in this config), and the two-cycle approximation is a pre-existing model limitation rather than something this line introduced.

`lib/api-client-react/src/local/local-first.ts:1811`

**What goes wrong.** Catalog benefits are explicitly per-anniversary-year (catalog.ts benefit id 269: "Up to $50 in statement credits each account anniversary year"). markBenefit (line 1322) stores `usedAt` but nothing anywhere reads it: grep for `usedAt` across lib/ and artifacts/ shows it is only written, never compared to a date. `artifacts/card-organizer/index.html:5`

**What goes wrong.** A low-vision user opens the wallet on a phone and tries to pinch-zoom to read a card's reward-rate detail or the 8-10px issuer badges. Android Chrome honors maximum-scale=1 and refuses to zoom; the content stays at whatever size it rendered. This is a WCAG 2.1 SC 1.4.4 (Resize Text) failure and it is a bad fit for the domain — the app displays balances, due dates and fee amounts that users specifically need to read carefully. The tag is usually copied in to suppress iOS's tap-to-zoom on form inputs, which is better solved by ensuring inputs are at least 16px.

**Fix.** Change to `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover" />`. If iOS input auto-zoom was the motivation, set a 16px minimum font-size on input/select/textarea in index.css instead.


## Refuted proposals

These were raised by a finder agent and then eliminated by an independent verifier. They are recorded so they are not re-reported later.

### Over-cap spend is hardcoded to 1% in calculateCashback while applySpendCapToRate uses the card's real default rate, so the two engines disagree

The quoted code is genuine — local-first.ts:922 hardcodes `baseAmount * 0.01` while applySpendCapToRate:3234-3235 uses `getDefaultCategory(card).rate` — and the catalog facts check out (I enumerated all 182 cards; exactly cards 36 and 112 have a default rate above 1% alongside a capped bonus category). But the failure scenario cannot occur. The cap branch at line 904 requires `parseSpendCap(matchedCategory.category)` to be non-null, and `matchedCategory` comes from `getCashbackCategory`, which exact-matches `transaction.category` against the catalog string and otherwise returns the default category. Transaction categories are restricted to 11 hardcoded strings (CATEGORIES at transactions.tsx:86 and the identical list at analytics.tsx:103 — the only two useCreateTransaction call sites, both bound to a Select with no free-text entry; backup import restores stored cashback without recomputing). A spend cap only exists when the category string itself contains "(up to $X/period)", which a plain name like "Gas" never does, and no catalog default category carries cap text. I scripted all 182 cards x all 12 possible transaction categories: 0 combinations reach the cap branch, so the line-922 code is unreachable today. The claimed numbers are also inverted: on Marriott Boundless, "Gas" falls through to line 931 and matches the default "Other" @ 0.02 x 0.7c/pt = $14.00 on $1,000 — exactly the value the finding calls correct and claims the bug destroys. The $7.00 figure only materializes if the cap branch runs, which it cannot. The finding itself concedes it is masked and only surfaces if a separate finding is fixed first.

### Month-end clamping in dueDateForCycleEnd can pull the payment due date before the statement even closes

The quoted code exists verbatim at local-first.ts:1492-1507, but the failure it claims cannot occur. The same-month branch is taken only when dueDay > closingDay, so the due date is min(dueDay, daysInMonth) and the cycle end is min(closingDay, daysInMonth) — the due date is therefore always >= the cycle end. I brute-forced all 31x31x12 (closingDay, dueDay, month) combinations for 2026 through the real dueDateForCycleEnd/dateOnDayOfMonth logic: 0 cases with a due date before the cycle end, 10 with exactly zero gap. The headline ("before the statement even closes") is mathematically impossible. Two of the three claimed reproductions also produce different values than stated: (1) closingDay=30, paymentDueDay=31 on 2026-04-20 gives daysUntilDue = 10, not 0, so the claimed false "due soon" warning does not fire (wallet.tsx:1537 requires visibleDaysUntilDue <= 5 AND hasDueAmount); daysUntilDue only reaches 0 on Apr 30 itself, the day the user's own settings say payment is due. (2) The "realistic" close-on-the-3rd/due-on-the-31st case is misanalyzed — a statement closing Feb 3 with due day 31 clamping to Feb 28 is standard last-day-of-month semantics giving a 25-day grace period; there is no basis for the claim that Mar 3 is the issuer's real due date (Mar 3 is the next closing day, not a due day). What remains is only the 10 degenerate combos where both days clamp to the same month-end (closingDay 28-30 with dueDay 29-31), reachable only if the user configures a 1-3 day grace period, and even there the result (due = last day of month = closing day) is the consistent consequence of those settings rather than a computation error.

### Stored state with an unrecognized schemaVersion is overwritten with defaults instead of being preserved — no migration, no quarantine

The quoted lines exist verbatim (332, 381, 425), but the defect cannot occur in this codebase. (1) The trigger is unreachable: `schemaVersion` is declared as a TypeScript literal type `schemaVersion: 1` (line 52), and every single write path funnels through `normalizeLocalState`, which hardcodes `schemaVersion: 1` at line 282 AFTER the `...parsed` spread, so it overrides any incoming value. `writeIndexedDbState` has no callers outside `writeState`/`queueIndexedDbWrite` and lines 416/425 — there are no other IndexedDB writers in `lib/` or `artifacts/`. Git history across all commits shows schemaVersion has only ever been the literal 1; a v2 has never shipped. So no code that has ever existed can create a stored record with schemaVersion !== 1. The failure requires a hypothetical future release. (2) The one non-hypothetical scenario the claim offers — localStorage corruption — is actually HANDLED, and the claim's "no rescue copy" assertion is factually false. On corrupt localStorage, `readLocalStorageState()` returns null (line 384), then lines 420-423 read the IndexedDB record and restore it back into localStorage, returning early. IndexedDB IS the rescue copy. If IndexedDB instead errors (request.onerror line 325, or openLocalDatabase reject line 301), the promise REJECTS, landing in the catch at line 426, which returns without writing anything — no overwrite happens, contrary to the claim. If IndexedDB merely has no record (`!value` -> resolve(null)), there is nothing to preserve. In every reachable path, line 425 writes defaults only when there is genuinely nothing to lose. (3) "No rescue copy" is further wrong: a full backup export/import feature exists at lines 431-478, and the code comment at line 405 explicitly names backups "the durable fallback". STORAGE_KEY is also already namespaced "oh-my-card:local-state:v1" (line 25), so a future v2 would naturally use a different localStorage key. The only genuine residual is that the IndexedDB record key is the unversioned "primary" (line 29), which a hypothetical future v2 would collide on — a forward-compatibility design note, not a live high-severity data-loss bug.

### Backup export reports success even when the file is empty or the download was cancelled

Both alleged mechanisms fail verification. (1) "Empty file": serializeLocalDataBackup() (local-first.ts:442) always emits well-formed JSON and can never produce a zero-byte file. The defaultState() fallback in readState() (line 388) is the same single source of truth backing every UI query (listWalletCards, transactions, dashboard summary — 20+ readState() call sites, no in-memory cache), so if it degraded to defaults the entire app UI would render empty as well; the export mirrors exactly what the user sees, creating no false belief. That half of the claim is also explicitly derivative of other findings rather than a defect at data.tsx:76. (2) "Revoke before commit": per the HTML spec, blob-URL navigation captures the blob URL entry synchronously during the anchor's activation behavior, so URL.revokeObjectURL() on the next statement does not cancel a committed download in current Chrome/Firefox/Safari; the setTimeout-before-revoke idiom is legacy defensiveness, and no actual failure can be demonstrated from this code. (3) "Cancellation": the primary showSaveFilePicker path is correct — it awaits createWritable/write/close and returns on AbortError without a success toast (data.tsx:116-127). Only the fallback path toasts unconditionally, and no browser API exists to report anchor-download completion or cancellation, so that is an inherent platform limitation, not a defect. At most this is a low-severity optimistic toast in a fallback path, not a medium-severity silent backup failure.

### Time-range tabs overflow and get clipped at 375px

The quoted markup is accurate (analytics.tsx:1110-1115, labels at :81-86, TabsTrigger base at ui/tabs.tsx:30, main overflow-x-hidden at app-layout.tsx:29), but the claimed layout failure does not occur.

1) The core mechanism is wrong. Tailwind v4's `grid-cols-4` emits `grid-template-columns: repeat(4, minmax(0, 1fr))` — verified in the installed compiler (tailwindcss 4.2.1, node_modules/tailwindcss/dist/lib.js: `handleBareValue: ... repeat(${s}, minmax(0, 1fr))`). Per CSS Grid §6.6, a grid item's automatic minimum size is content-based only if it spans a track whose *min* track sizing function is `auto`; here it is explicitly `0`, so `min-width: auto` resolves to 0. The tracks do NOT refuse to shrink and the TabsList never exceeds its container. `overflow-x-hidden` on <main> therefore clips nothing.

2) The claimed symptom is impossible with these classes. Neither TabsList nor TabsTrigger sets `overflow: hidden` or `text-overflow: ellipsis`, so "This Quart…" cannot render. Overflowing nowrap text in an `inline-flex ... justify-center` box spills symmetrically and stays painted; it is not truncated.

3) The arithmetic is also off. Available width at 375px is 375 − 32 (main p-4) − 32 (section p-4) = 311 for the TabsList border box; minus its own `p-1` (8) = 303... actually the TabsList is `w-full` = 311 border-box, content 303 → wait, correct chain: main content 343, section content 311, TabsList w-full = 311 border-box, minus p-1 = 303 content → each of 4 tracks = 75.75px (not 76 of a 303 minus-p-1 figure the claim double-counted; either way ~74-76px).

4) Measured real label widths (SF semibold 12px, macOS Core Text): "This Month" 65.8, "This Quarter" 73.7, "This Year" 54.4, "Lifetime" 47.8. Laying these out centered in ~74-76px tracks: every label stays inside the 303px TabsList; the rightmost tab ("Lifetime", the narrowest at 47.8px) has ~13px of slack on each side and is never cut off; adjacent labels do not overlap (6-12px gaps). The active pill is a full track wide, so the selected state remains unambiguous.

Residual (much smaller) truth: "This Quarter" at 73.7px effectively consumes the entire 73.75px pill, so its `px-3` padding is visually eaten and the text touches the pill edge; with the Inter fallback (non-Apple platforms) it would bleed ~2px past the pill and nearly touch the "This Month" label. That is a cosmetic tightness nit (low, "cramped"), not clipping/truncation, and the reported mechanism, symptom, and severity are all wrong — so I score the finding as not real.
